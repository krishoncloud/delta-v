    How it works

    What Delta-V is for, the flow it expects, and where the saving is meant to come from.

    The problem

    Simulations cost money and time. Teams often plan a large batch of runs up front, many of which turn out not to be needed. Delta-V is meant to get more out of the runs you already have, so the next batch can be smaller and better aimed.

    The flow

    1. Bring the runs you have. One ZIP: the settings of each run, its starting and final fields, and which runs are for training, checking and calibrating.
    2. The model adapts. A model pretrained on other fluid simulations is fine-tuned to your study, then checked on runs it never saw.
    3. Explore without simulating. Ask for any setting inside your study's range and get the predicted outcome with a 90% prediction interval.
    4. Set your limits, run only the useful few. You say which settings range matters, how accurate is enough and how many runs you can afford. Delta-V suggests a small batch inside those limits, usually 4 to 8 runs, that fills the gaps. You run them in your own solver and add the results.
    5. Stop when it is good enough. When the 90% prediction intervals are inside the accuracy you need across your range, you likely have enough runs for that question. Confirm with a few solver runs

    Where the saving is meant to come from

    Smaller batches

    Ask for a handful of well-placed runs instead of a large blind sweep.

    Stopping early

    A stop signal tells you when more runs would not change the answer much.

    Explore without another solver run

    Trying a new setting is a prediction, not a simulation. Predictions still use some compute.

    What it asks of you

    Before the first prediction the model needs about 59 finished runs: 8 to train on, 12 to pick the best version of the model, and 39 to calibrate the prediction intervals. That cost is paid once per study. In our tests the model was already accurate with 16 training runs.

    When you add finished runs later, they are saved as a new version of your study (version 2, 3 and so on). The model you already have keeps working; it still uses version 1. Re-adapt on a GPU, about 3 to 4 minutes, to include the new runs.

    Where it stands today

    • More accurate than standard methods when only 8 to 16 training runs are available.
    • Calibrated 90% prediction intervals that held up on 200 unseen cases.
    • A stop signal that never stopped too early in our tests.
    • Lower total cost is showing promising early results, and we are working on it further with real solvers. The budget numbers below are your own scenario.

    What a simulation run costs

    Delta-V works alongside your solver. It aims to cut how many runs a study needs, so it matters most when each run takes hours. On the worked example here a solver run takes about half a second, so there is nothing to save there.

    ApproachLicenceCompute for one run
    OpenFOAM Free and open source. Cloud compute only, about $0.03 to $0.10 per core-hour. One published example: a 20-million-cell steady case on 48 cores for about 10 hours cost about €24.
    Commercial solvers such as Ansys Fluent and Simcenter STAR-CCM+ Not published. Third-party estimates for Fluent are about $20,000 to $40,000 per user per year, plus HPC packs beyond 4 cores. STAR-CCM+ pay-per-hour licensing was reported at about $22 per wall-clock hour. The same compute as OpenFOAM, plus licence time while the run is open.
    Delta-V (prototype) Not priced yet. About half a second of CPU per predicted setting on this demo server. Adapting the model to a study takes about 3 to 4 minutes on one GPU. It still needs 67 finished solver runs per fit.

    Research

    The tests behind Delta-V, what each one showed, and what comes next. Every number comes from recorded research runs on one generated flow study.

    Loading…

    What we found

    • Accurate with few runs. With 16 training runs, 597 of 600 held-out settings were within tolerance, and error was clearly lower than standard methods at 8 to 16 runs (Tests 6, 8 and 8b).
    • Honest uncertainty. The calibrated 90% prediction intervals covered 91.5% of 200 unseen cases (Test 7).
    • Knowing when to stop. The stop signal was right in 15 of 15 runs, never too early (Test 8). An exploratory replay of the next-run picker saved about one batch at tighter targets.

    All measured on one generated 2D flow study type, not customer data.

    The tests behind it

    Each test answered one question. Later tests built on what earlier ones showed.

    1. 1–3

      Does earlier learning help on a fluid the model never saw?

      How we tested

      We held one fluid system (compressible Euler flow) out of pretraining, then trained two copies on the same small amount of its data: one starting from the pretrained model, one from scratch.

      The pretrained start reached a final loss of 0.0089 against 0.0107 from scratch, 16.3% lower, after 30 training passes.

      Owner-reported run on one setting of the gas constant, without saved checkpoints. A fuller rerun is planned.

      Owner-reported
    2. 4

      A fair baseline to compare against

      How we tested

      We built outcome tables for the three training systems and measured standard methods (mean, linear and Gaussian process) on them, so later results had something honest to beat.

      Baseline built
    3. 5

      Can the model predict outcomes from settings?

      How we tested

      We connected the pretrained field model to scalar outcomes, so it takes a setting and returns a number, and checked every stage end to end on a GPU.

      All eight checks passed. On that simple test case the standard method was still more accurate, which set up Test 6.

      Pipeline check
    4. 6

      Does pretraining help on a new problem?

      How we tested

      A new generated flow study with three settings and two outcomes. We compared the pretrained model with a from-scratch model and a Gaussian process at 8, 16, 24 and 32 training runs. A first round showed the models were undertrained, so we reran with longer training.

      The pretrained model reached the accuracy target with 16 runs; the other methods needed 24. At 8 runs its error was about a third of the Gaussian process's. From 24 runs on, the Gaussian process caught up and pulled ahead.

      Measured on generated study
    5. 7

      Can the prediction intervals be trusted?

      How we tested

      Five copies of the model each make a prediction; how much they disagree gives a raw range. We tuned that range on 39 separate runs, locked the rule, then tested it on 200 unseen cases.

      The 90% prediction intervals contained the true result 91.5% of the time. The raw ranges alone were too narrow, which is why the tuning step stays.

      Measured on generated study
    6. 8

      Does choosing the next runs save runs?

      How we tested

      Five complete workflows, each starting from 8 runs and adding 8 at a time, repeated three times. Each one decided for itself when to stop.

      Spreading runs evenly hit the accuracy target at 16 runs in all three repeats. The stop signal was right every time: 15 of 15 stops, none too early. Total runs used ended up level with the best standard workflow.

      Measured on generated study
    7. 8b

      A tougher baseline, and a cheaper way to calibrate

      How we tested

      We compared against a stronger field-based method (POD with Gaussian processes) on the same runs, and tried tuning the ranges without the 39 extra runs.

      The pretrained model was clearly more accurate at 8 and 16 runs, with error about 31% lower for kinetic energy and 52% lower for pressure at 16. The cheaper calibration came out too cautious, but calibrating on the 12 checking runs looks like a promising shortcut.

      Measured, retrospective
    8. +

      A smarter next-run picker

      How we tested

      We replayed the whole loop with every candidate solved in advance, comparing random picks, even spreading, uncertainty only, and a picker that adds runs only where the range is still too wide.

      The picker was never worse than the alternatives and saved about one batch of 4 runs at the tighter accuracy targets. It also asks for fewer runs as the model improves: 5 at 16 runs, 3 at 24.

      Exploratory replay

    Where it stands

    What holds up

    • More accurate than standard methods at 8 to 16 runs, in four separate tests.
    • Calibrated 90% prediction intervals, measured at 91.5% coverage.
    • A reliable signal for when you have enough runs.
    • A locked, repeatable test process: rules fixed before results were seen.

    What comes next

    • Run the workflow on a real customer solver, where each run is expensive.
    • Lower total cost is showing promising early results: the next-run picker already saved about one batch at tighter accuracy targets. We are building on it.
    • Make calibration cheaper using runs you already supply.
    • Support more study types: so far, one generated 2D flow family on a 64 × 64 grid.

    With many runs (24 or more), standard methods match or beat the pretrained model. Delta-V's advantage is when runs are scarce.

    What are these numbers testing?

    Relative error (rel. L2): total prediction error compared with the size of the reference field. Lower is better; it is not a percentage accuracy score.

    Typical error (RMSE): error magnitude in this field’s simulation units. Different fields have different scales.

    Structure match (SSIM): local image structure similarity. 1 is an exact match; it does not prove conservation or physical correctness.

    These scores test one next-step prediction on a training example. Parameter-slider estimates, unseen trajectories, long rollouts, and transfer to Euler are not validated by them.

    Errors use full-precision fields and ground truth resampled to 256 × 256. Self-imposed v1 target: scalar and pressure rel. L2 <15%; velocities have no quantitative target. This target is not a held-out validation claim. Display colors are quantized and can clip predictions outside the reference range.

    What a time instance means

    Each sample contains five consecutive snapshots from one simulation trajectory. Local frames t₀–t₃ are the model input; t₄ is the next-state reference. Physical times come from the sample metadata, in simulation code units. A local frame number is not physical time.

    The source start index identifies the first frame in the window. Each catalog entry lists every timestamp and its spacing. The extraction did not retain the original trajectory ID or file path, so these sample IDs are not a complete trajectory catalog.

    All fields are resampled to 256 × 256 for the model. The viewer preserves the physical domain’s aspect ratio. The top timeline loops the five recorded snapshots. Autoregressive rollout uses three separate official-test clips (IDs begin rollout-test-) with eleven recorded frames each: f0–f3 seed the model and f4–f10 are the reference.

    Training scale. The served checkpoint was trained on bounded slices of The Well at prototype budget, not on the full trajectory sets. This is the main reason accuracy and rollout horizon are where they are; see the Model page.

    euler_multi_quadrants_openBC is a fourth fluid system held out entirely from joint SEM pretraining. Pretraining used turbulent_radiative_layer_2D as the primary set with shear_flow and rayleigh_benard as joint co-training sets.     Artifact status

    • No fine-tuned checkpoint exists. Neither the pretrained-start arm nor the from-scratch arm was saved or pushed. Confirmed directly against the checkpoints/ folder of the HF dataset repo. Only the losses above survive, which is why this page is static and Euler cannot run live.
    • Normalization stats do exist on HF (stats/euler_multi_quadrants_openBC.npz), so that piece is not a blocker for wiring Euler live later.
    • No parametric table for Euler exists, unlike the three live systems. Its single dial (gamma) is defined in code but was never built into a servable table.

    Euler in the shared representation

    • Native grid 512 × 512, resampled to 256 × 256 for the model.
    • Five raw fields; four map into the canonical [scalar, pressure, velocity_x, velocity_y] vocabulary and one raw field has no canonical slot and is dropped.
    • Raw velocity channels store momentum-like quantities; they are divided by density on the way in to recover true velocity (derive_velocity). This transform is applied once to the seed frames only; predictions are never round-tripped through it.
    • One dial: gamma.

    What this experiment does and does not test

    It compares two starting points for full-model training. It does not test frozen-backbone learned adapters. It is evidence in the direction of transfer to another fluid system, not proof of generalization to arbitrary physics. A trajectory-separated rerun and saved checkpoints are needed for stronger claims.

    How each physics domain is meant to mature

    1. Single system (SEM): a single-system engineering-model experience. The three live systems are presented at this maturity level; their current implementation shares one jointly trained checkpoint.
    2. Several systems: demonstrate reliable shared learning across systems within fluids. Sharing weights alone does not establish that milestone.
    3. One unseen system: demonstrate generalization to one unseen fluid system, not universal physics generalization.
    4. Validated engineering model (LEM): a broader, rigorously validated engineering model within that domain; not claimed here.

    The Euler result is evidence in the direction of the next step, not a claim that Delta-V has reached it. Every future domain (solid mechanics, heat transfer, electromagnetics) is meant to repeat this same climb with the same tooling, the same honesty rules and its own measured evidence. Fluids is simply the domain we started with.

    Next: fix gamma selection, rerun both arms, save checkpoints and provenance, then connect a real side-by-side. A learned-adapter arm remains a separate future experiment.

    What Delta-V does today

    Bring compatible simulation runs, adapt a pretrained Fourier Neural Operator to them, explore settings you have not simulated with calibrated intervals, and choose the next batch of runs. That workflow lives in the Workbench, for one supported study type: a 2D periodic flow on a fixed 64 × 64 grid. Its research basis is on the Evidence page.

    The sections below explain the earlier work that led here: the shared next-frame model in the Model demo, the rollout view and the Euler probe. They are history and context, not additional supported study types.

    OverviewApproachLimitationsWhat we triedWalkthrough

    A system for learned engineering surrogates, built one physics domain at a time.

    Delta-V is not a fluids tool. It is the scaffolding for serving, measuring and honestly presenting learned approximations of physical systems, and fluid dynamics is the first domain we are running through that scaffolding. Each domain gets its own data, its own checkpoint, and its own climb up the same maturity ladder. What carries across domains is the workflow: a fast parameter-based estimate, a neural next-state prediction, a bounded rollout, and a reference comparison beside every result so you can see exactly where the model agrees with simulation and where it does not.

    The project began in a software engineering lab. This public prototype is an invitation to test the interaction and understand its usefulness. The live fluids model uses only 2D data from The Well and complements high-fidelity simulation. Its output is not validated industrial simulation.

    Fast estimates, with a reference you can inspect.

    The distinction is the workflow: a numeric parameter explorer and a field-comparison viewer share one interface across three fluid systems. Open code and identifiable data make the implementation inspectable. This is a design choice, not evidence of superior accuracy or speed over other tools.

    The parametric tier interpolates outcome tables for flux and turbulent velocity. The field tier uses a Fourier Neural Operator (FNO) with per-system preprocessing. Changing an outcome dial does not generate a new field initial condition: field prediction uses a selected recorded sample.

    Current stage

    An experimental multi-system fluid prototype: three served systems, one shared field checkpoint, six training demonstration windows, three official-test rollout clips with up to 30 generated steps, and browser-local history. Our starting point was the single-system engineering model (SEM). This shared serving setup is an early step toward a broader fluid model, but a validated large engineering model (LEM) requires evidence of generalization that this prototype does not yet provide.

    The bottleneck is training scale, not architecture. The served checkpoint was trained at prototype budget on bounded slices of The Well, not on the full trajectory sets. That is the honest reason for the current accuracy and for how quickly rollout error grows. The rollout horizon (how many frames the model can generate from four inputs before crossing the error target) is the number we expect to move as training scales, and it is how we intend to measure that.

    The research path is to compare per-system baselines with joint training, then evaluate generalization to unseen fluid systems (the Euler probe is the first such measurement), then open the next domain and repeat. Cross-domain or 3D generalization is not claimed.

    The comparison is part of the product.

    • Uneven prediction quality. Inspect relative L2, RMSE and SSIM per channel in the measured results below. The self-imposed v1 target is strictly relative L2 <15% for scalar and pressure. Some windows miss that target. Velocity channels are directional structure only; no quantitative target for this release.
    • Six short windows. Two examples per system, drawn from training slices. They demonstrate behavior, not out-of-sample generalization. Each has four input snapshots and one reference next state.
    • Prototype-scale training. The checkpoint was trained on bounded slices of The Well, not full trajectories. More training data and budget, not a new architecture, is the main lever left for the fluids model.
    • Bounded rollout, short reference. Up to 30 generated steps on three official-test clips, but measured error exists only through f10. Beyond that there is no ground truth and no error is reported. The top timeline still shows recorded frames only.
    • Fixed model grid. Fields are resampled to 256 × 256. Images use 8-bit colors; metrics use full-precision fields before display quantization.
    • Parameter-estimate evaluation is open. Field errors do not validate table interpolation. The parametric tier needs its own accuracy evaluation.
    • Prototype hosting and storage. Startup can take a minute or two after sleep. History lives in your browser, without synchronization or saved full-resolution result arrays.

    Choices, experiments, and lessons.

    A common representation for different fluids

    Density, buoyancy, and tracer map to a shared scalar channel alongside pressure and x/y velocity. Per-system normalization and fixed preprocessing adapters let the same pipeline handle radiative cooling, convection, and shear mixing. These adapters map data; they are not learned neural modules. The served FNO weights are fully shared.

    Spectral prediction plus table interpolation

    FNO was selected as a neural-operator baseline for spatial fields. A lightweight interpolator handles numeric outcomes without running the field model. Both are available here so their different roles stay visible.

    A checkpoint-selection correction

    During development, the file labeled “best” retained epoch-3 weights while later training reached epoch 59 with lower validation loss (0.0366 → 0.0251). Inference was compared and the artifact corrected. The live epoch appears on the Model page. Validation loss is not the same as the per-field error shown here.

    An Euler-system research probe

    The code retains an adapter for euler_multi_quadrants_openBC but excludes it from the served fluid family. This was explored as a generalization probe. The supplied notebook implements full fine-tuning versus training from scratch on Euler. The owner subsequently supplied a 30-epoch result: 0.0089 versus 0.0107 final loss, with a reported 16.3% lower error for the pretrained start. Only one gamma value was covered instead of four intended; checkpoints were not saved. See the two-arm probe and caveats. A frozen-backbone learned-adapter arm, a trajectory-separated evaluation and comparisons across data fractions are new work. The two-arm result points in the direction of transfer; learned-adapter advantage is not established.

    Next questions

    Which comparisons help people judge a prediction? Where do errors concentrate? Are more sample windows or longer rollouts useful? Broader evaluation and clearer data provenance will guide the next iteration.

    Your first exploration.

    1. Choose a physical system. Select cooling-driven turbulence, convection, or shear flow. Fields, samples, and ranges update together.
    2. Try the instant explorer. Adjust the logarithmic sliders; estimates update after you pause dragging for 150 ms. Estimate outcomes also lets you retry. These are table-based estimates in simulation code units.
    3. Inspect a sample. Choose a bundled window, field, and frame. Each view has a numeric color scale and preserves the physical aspect ratio.
    4. Run a prediction. Four history frames predict the fifth. Compare prediction, reference, and signed prediction-minus-truth. Timeline selection does not change this fixed target. The fixed one-step predictions are computed at startup and cached. Repeated requests reuse the result; they do not run the model again.
    5. Read the errors. Relative L2 compares error magnitude with reference magnitude; lower is better. RMSE measures typical error magnitude in the field’s units. SSIM measures structural similarity, with 1 denoting an exact match. Near-zero references can make relative error hard to interpret.
    6. Inspect and revisit. Zoom, expand, or download the current field. History saves metrics and a comparison preview; reopening the sample and predicting again reuses the cached prediction for the current model.
    7. Explore the rest. Datasets explains domains, parameters, windows, source indices, and times. Model describes the architecture. Settings controls appearance.
